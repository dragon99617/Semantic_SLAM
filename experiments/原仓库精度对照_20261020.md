# FAST-LIVO2 原仓库精度对照资源核查

核查日期：2026-10-20。结论：**原作者提供了可直接核对的 NTU-VIRAL 真值、作者估计轨迹、转换脚本和 RMSE 表；论文另有多算法精度对照。但尚未找到我们正在使用的 Retail Street 的公开定位真值或对应 ATE 数值，现阶段不能宣称本地 ROS 2 运行达到作者精度。**

本次只查阅资料和代码，没有启动新的里程计实验、下载大型数据包或修改算法。原仓库已克隆到 `third_party/FAST-LIVO2_original/`，提交号为 `0d2c0346107b75b59934975adec9a6eeeb913c64`。其中的 NTU-VIRAL 评测资料也已经随当前社区 ROS 2 源码保存在本地，20 个文件逐一 SHA-256 比较完全相同。之前阶段一评估的“没有匹配真值”是针对 Retail Street 运行，不应理解为整个项目没有精度评测资源。

这些是作者在仓库中发布的结果，**不是本地 ROS 2 移植版的测量结果**。目录里的 `*_gt.txt` 是转换为 TUM 格式的真值；`*_prism.txt` 是作者 FAST-LIVO2 估计结果经棱镜偏移补偿后的轨迹。不能把后者作为独立测量真值。

作者给出的评测命令：

```bash
evo_ape tum eee_01_gt.txt eee_01_prism.txt -a --plot --plot_mode xyz
```

命令对齐轨迹后计算平移 APE，关注 RMSE；未开启尺度校正。本次没有运行 evo 或独立复算上表。

## 2. 论文还有多算法精度对照，必须与仓库结果分开

[主论文 arXiv v2，Table II、IX-B](https://arxiv.org/html/2408.14035v2#S9.T2) 比较了 NTU-VIRAL、Hilti 2022/2023 共 25 条序列；指标为绝对平移误差 RMSE，单位米。例：

| 数据与序列 | FAST-LIO2 | R3LIVE | FAST-LIVO | FAST-LIVO2 默认版本 |
|---|---:|---:|---:|---:|
| NTU-VIRAL eee_01 | 0.212 | 0.072 | 0.191 | 0.068 |
| NTU-VIRAL eee_02 | 0.172 | 0.059 | 0.132 | 0.051 |
| NTU-VIRAL eee_03 | 0.213 | 0.078 | 0.192 | 0.068 |
| Hilti 2022 Construction Stairs | 0.320 | 0.784 | 0.241 | 0.016 |

同一 eee_01，论文默认版本为 6.8 厘米，仓库 README 为 2.71 厘米。资料没有在该 README 解释两批数字的差异，不能默认它们来自相同版本、参数和评测处理。论文默认关闭法向细化，而当前上游 NTU 配置中 `normal_en: true`，也提示发布代码与论文默认实验设置需要逐项核对；这不足以单独解释全部差值。

论文 Table II 默认版本平均值写为 0.045 米，正文 IX-B 写为 0.044 米，两处有不一致；不将其混写为同一确定基准。

此外，[主论文 X-B、补充材料 I-E](https://arxiv.org/html/2408.14035v2) 提供 MARS-LVIG 的 RTK 对照：HKairport01、HKisland01 的 FAST-LIVO2 APE RMSE 分别为 0.64、0.27 米；AMvalley03 的顺序更新版本为 0.68 米。这些适用于对应飞行序列，不能用于 Retail Street 验收。

## 3. Retail Street 能比什么

论文补充 Table S1 将其列为约 2 分 15 秒的室外返回起点序列；主文展示彩色地图，Table III 给出处理耗时，补充 Fig. S5 使用它做曝光估计验证。**曝光时间真值不等于定位真值；处理耗时也不等于精度。**

本次检查的原仓库、论文和作者公开数据目录中，没有找到该序列的定位真值轨迹文件或专属 ATE 对照值。这是“尚未找到”，不是证明任何渠道都没有。当前本地 bag 也只有图像、LiDAR 和 IMU。

因此，我们现有结果能用于运行完整性、地图外观和返回起点一致性检查。起终点差异不能替代整段轨迹 ATE；也不能拿 NTU 的厘米级结果直接验收这条街景序列。

作者 README 现在还通过 [Global-LVBA 第 4 节](https://github.com/xuankuzcr/Global-LVBA#4-dataset-download) 提供了新的 [FAST-LIVO2 原始数据 Google Drive 目录](https://drive.google.com/drive/folders/1bf5LQ8iSxw-fD8BObZmouw7lRxNacfrA)。本次确认目录可列出 `Retail_Street.bag`，未下载内容，也未与现有社区转换包作消息或哈希比对。

## 4. 若补做一次可量化的 ROS 2 精度核验

建议选 NTU-VIRAL 的一条序列，比较“本地移植输出—测量真值”，再对照作者同序列结果。eee_01 与作者示例一致；若优先减少下载量，eee_03 是论文覆盖的序列，官方列出的压缩包为 4.3 GB、181.4 秒，eee_01 为 8.7 GB、398.7 秒。来源：[NTU 官方数据页](https://ntu-aris.github.io/ntu_viral_dataset/)。本次没有启动下载。

评测时需要做到：

1. 使用对应 NTU 的 LiDAR、左相机与 IMU 配置，保留版本、参数和播放速率；检查 Ouster 字段、图像传输类型和 ROS 1→ROS 2 转换兼容性。原仓库提供 `config/NTU_VIRAL.yaml`、相机参数及启动文件，当前移植仓库也有对应配置。
2. 输出传感器时间的 TUM 轨迹。现有代码的 `evo.pose_output_en` 可以输出该格式；不要用我们当前采集的系统时间 `observed_odometry_wall_time.tum` 做时间匹配。
3. 按 [原作者 evaluate_viral.py](https://github.com/hku-mars/FAST-LIVO2/blob/0d2c0346107b75b59934975adec9a6eeeb913c64/Log/result/ntu_viral/evaluate_viral.py) 将 IMU 位置转换到测量棱镜位置：`p_prism = p_imu + R_imu * [-0.293656, -0.012288, -0.273095]`，单位米。脚本默认文件名硬编码为 eee_01；换序列需调整。脚本负责格式及参考点转换，不负责计算 RMSE。
4. 统一时间关联、对齐与有效区间。数据集[官方评测教程](https://ntu-aris.github.io/ntu_viral_dataset/evaluation_tutorial.html) 采用真值插值和刚体对齐；仓库示例使用 evo 时间关联。两套处理不能未经核对就认定等价。报告实际关联容差、匹配点数和时间覆盖，固定评测规则后比较。
5. 先报告平移 APE RMSE。NTU 这里提供的是棱镜位置真值；原作者转换脚本将真值四元数填为单位四元数，本地九份 GT 文件也确实如此，不能据此计算有意义的姿态误差。

NTU 官方还单独提供 [CSV 真值仓库](https://github.com/ntu-aris/ntuviral_gt)。Hilti 的真值在论文发表时需要走官方评测，因此就本地自行核验而言，NTU 的资料更直接。

核查文件列表、SHA-256 及与当前 ROS 2 仓库的逐文件比对见 [原仓库精度资源记录](原仓库精度资源_20261020.json)。
